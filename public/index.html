Self-hosted Bend compiler

A compiler written in Bend that emits C and JavaScript. Self-hosted means it can compile its own source—not that it is faster.

Start with a function that remembers a value. Follow it through checking, shared lowering and target code, then examine the measured costs.

Follow the captured value

A closure pairs code with values from its enclosing scope. In adder, x arrives later; k must travel with the returned function. Follow that same program across the compiler’s boundaries.

  1. Check: what does this program mean?

    k : U32 and x : U32; adder(k) : U32 → U32. Names resolve to their declarations and bindings. The resulting function is invoked once, respecting at-most-once (affine) use.

    resolved names + types + permitted uses

  2. Lower: what must execute?

    Make the captured k, the function body and the call explicit. Preserve lexical identity and evaluation order instead of rerunning an expression substituted during checking.

    capture k → bind closure → apply to x → return

  3. Emit: how does this target execute it?

    The JavaScript backend chooses functions, runtime calls and host-value adaptation. The C backend instead chooses physical layouts and its runtime calling convention. Both consume the same structured backend program.

Explanatory facts and operations, not a compiler IR dump or proof of heap allocation: a backend may specialize calls. An intermediate representation (IR) describes the program inside the compiler; lowering translates checked meaning into executable operations.

What checking guarantees, and what the targets still do

Checking parses modules, expands templates and checks types, resolved names and permitted value uses. Its contract requires structural termination checks subject to explicit unsafe exceptions. Erased bindings are not runtime values. Failure returns a diagnostic, not a partially checked program.

The successful CheckedProgram retains modules, signatures, scope metadata and checked occurrences. Shared lowering handles erasure, captures, direct or indirect calls and pattern flow. Backend blocks express bindings, branches, returns and tail calls; lexical regions share the continuation after a failed pattern case. Separate descriptors retain layout, display and host-interface metadata.

C

Computes physical layouts and sharing plans, builds runtime tables, and emits executable segments and continuations using the C runtime’s calling convention.

C planning and emission

JavaScript

Plans continuation captures and region frames, emits functions and runtime helpers, and adapts values at host boundaries. A continuation describes the work to resume after another computation.

JavaScript planning and emission

These are not just text printers. Both retain their own primitive operations and foreign-code integration. The compiler’s chunked Run/Stack execution protocol and the emitted JavaScript trampoline are execution machinery, not additional semantic IRs. A trampoline dispatches pending work instead of growing an unbounded chain of host calls.

Performance against the official compiler

This comparison is limited to loading, parsing, template expansion and checking the same selected compiler-source closure: 17 Bend modules and 35 foreign JavaScript files. This is a different input from the tiny closure demo; running that emitted JavaScript is not a compilation benchmark. Code emission, a C toolchain build and a complete self-compilation cycle are not measured here.

The cached native self-hosted compiler took 10.705× as long as the official TypeScript implementation on this checking workload: 27.707 s versus 2.588 s median source-processing time. Its sampled peak resident memory was lower in this cohort.

What makes this a compiler-shaped workload?

The admitted native runs processed 1,690,863 bytes of Bend source and 78,415 bytes of foreign JavaScript. A separate retained-source audit identifies interfaces with up to 50 arguments and a complete 66,793-byte resume dispatcher, with namespaces and foreign alternatives preserved: no stubbed bodies or dependencies, and no AST replay.

Those are source-shape observations, not runtime allocation measurements. CPU-coverage analysis was inconclusive; preserving large compiler structures does not establish matching CPU cost or make this an accepted universal performance proxy.

Validation

Historical self-compilation evidence

A native compiler compiled its own Bend source into a JavaScript compiler. That JavaScript compiler compiled the same source again. The two successive JavaScript images were byte-identical: 31,758,507 bytes, without normalization or output patches.

The behavior checks used 95 distinct fixtures—64 positive and 31 negative—across the seed and both emitted images. That is 285 executions, not 285 different tests. The recorded full-root validation covered 12,456 checked definitions and 13,050 validated events, with no excluded checks.

This evidence belongs to the historical compiler artifact. It is separate from the new check-only timings and does not establish a fresh fixed point for the current source, pure-C self-hosting, or correctness for every program.

What remains unproved

The front-end and backend laws are explicit contracts, not a mechanized proof of the whole pipeline. Not every numeric handle, lexical-scope invariant or metadata relationship is enforced by the carrier types, and there is no complete backend-IR validator. Shared IR does not establish full C/JavaScript parity, GPU/WASM preservation or constant total memory use.

Measurement method and source

The architecture above describes the linked source snapshot. The performance comparison instead uses a digest-bound, previously validated native executable, built with diagnostic -O1 optimization—not a freshly built current-source compiler or the official default C optimization.

The current-source authentication wrapper cannot authenticate that old build because lexer and driver inputs have changed. The measurement uses the artifact’s documented raw check-only interface and identifies its bytes explicitly; it does not claim new build qualification. The official checker’s source bytes match the retained kernel used for this workload.

These are sampled guards, not hard allocation quotas or exact allocation peaks.
Completion checks
All six samples completed with their guards satisfied. Official runs covered the 52-file input map, 2,420 definition bodies and 2,954 validation events, with no holes or unchecked bodies. Native runs returned CheckSuccess for all 17 modules. No checks were excluded and no outputs were patched. The 35 foreign JavaScript files belong to the retained closure; no JavaScript emission or execution is timed.
