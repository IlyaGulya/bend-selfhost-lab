Self-hosted Bend compiler

A compiler written in Bend that emits C and JavaScript. Self-hosted means it can compile its own source; it does not mean it is faster than the official TypeScript implementation.

This report explains the checked program boundary, the shared lowering used by both backends, and the storage they own. It separates the current source architecture, a fresh check-only performance comparison, and historical self-compilation evidence.

Compiler pipeline

An intermediate representation (IR) is the compiler’s internal description of a program. This implementation separates a checked front-end IR (FIR) from a structured backend IR (BIR). Lowering translates the checked description into explicit executable operations.

Check the source and retain the decisions

The front end parses modules, expands templates and checks types, names and permitted uses of values. Its contract also requires structural termination checks, subject to explicit unsafe exceptions. An affine binding may be used at most once; an erased binding is not a runtime value.

A successful check returns an owned CheckedProgram: the source arena, checked modules, signatures and scope metadata. Checked occurrences retain resolved declarations, types, quantities and children. Failure returns a diagnostic, not a partially checked program.

Checked programFront-end contract

Lower once, then select a target

Shared lowering decides erasure, operand evaluation order, closure captures, direct or indirect calls, and pattern control flow. A closure pairs code with values captured from its enclosing scope. Local references keep their lexical identity rather than repeating a computation substituted during type checking.

The resulting backend IR contains operands, operations, declarations and code bodies. Its structured blocks express bindings, branches, returns and tail calls—calls with no remaining work in the caller. Lexical regions share the continuation after a failed pattern case instead of duplicating the remaining cases. Separate type descriptors provide layout, display and host-interface metadata.

How this differs from the official compiler

The official TypeScript compiler already has core terms, checked annotations and intermediate forms. Its backend reads checked bodies; its C analysis repeats until ownership and sharing facts settle. That is a backend fixed point, not repeated source type checking.

The distinction here is an explicit handoff from an owned checked program through one shared lowering into a separate structured backend program. It reorganizes semantic decisions and storage ownership; it does not establish that the official compiler lacks an IR or that the new design must be faster.

Both backends still do target-specific work

C

Computes physical layouts and sharing plans, builds runtime tables, and emits executable segments and continuations using the C runtime’s calling convention.

C planning and emission

JavaScript

Plans continuation captures and region frames, emits functions and runtime helpers, and adapts values at host boundaries. A continuation describes the work to resume after another computation.

JavaScript planning and emission

These are not just text printers. Both retain their own primitive operations and foreign-code integration. The compiler’s chunked Run/Stack execution protocol and the emitted JavaScript trampoline are execution machinery, not additional semantic IRs. A trampoline dispatches pending work instead of growing an unbounded chain of host calls.

Backend and execution contracts

Data-oriented storage and ownership

Typed-array pools
The source arena owns separate array-backed pools for nodes, patterns, binders, names and metadata. Numeric handles refer into this storage; start/count slices identify ranges in tapes.
Explicit ownership
Checking hands one source owner to lowering. Moving an affine owning record transfers it rather than copying its arena. The backend receives an executable program, not the checker or its source arena.
Reusable scratch
Declaration-local temporary storage is rewound and reused. Epochs invalidate transient substitution-memo entries; reusable analysis plans avoid rescanning the same continuation suffix at every use.

This is not an all-flat or zero-allocation compiler: checked occurrences and backend blocks remain recursive, and growing a pool can copy its storage. These mechanisms describe the design, not a measured garbage-collection benefit or an explanation of the timing difference.

Performance against the official compiler

This comparison is limited to loading, parsing, template expansion and checking the same selected compiler-source closure: 17 Bend modules and 35 foreign JavaScript files. It does not measure code emission, a C toolchain build or a complete self-compilation cycle.

The cached native self-hosted compiler took 10.705× as long as the official TypeScript implementation on this checking workload: 27.707 s versus 2.588 s median source-processing time. Its sampled peak resident memory was lower in this cohort.

These are single-host results from an Apple M1 Max, not a universal slowdown factor. The selected source workload does not establish code-generation speed or end-to-end compiler performance, and this experiment does not isolate why the implementations differ.

Validation

Historical self-compilation evidence

A native compiler compiled its own Bend source into a JavaScript compiler. That JavaScript compiler compiled the same source again. The two successive JavaScript images were byte-identical: 31,758,507 bytes, without normalization or output patches.

The behavior checks used 95 distinct fixtures—64 positive and 31 negative—across the seed and both emitted images. That is 285 executions, not 285 different tests. The recorded full-root validation covered 12,456 checked definitions and 13,050 validated events, with no excluded checks.

This evidence belongs to the historical compiler artifact. It is separate from the new check-only timings and does not establish a fresh fixed point for the current source, pure-C self-hosting, or correctness for every program.

What remains unproved

The front-end and backend laws are explicit contracts, not a mechanized proof of the whole pipeline. Not every numeric handle, lexical-scope invariant or metadata relationship is enforced by the carrier types, and there is no complete backend-IR validator. Shared IR does not establish full C/JavaScript parity, GPU/WASM preservation or constant total memory use.

Measurement method and source

The architecture above describes the linked source snapshot. The performance comparison instead uses a digest-bound, previously validated native executable, built with diagnostic -O1 optimization—not a freshly built current-source compiler or the official default C optimization.

The current-source authentication wrapper cannot authenticate that old build because lexer and driver inputs have changed. The measurement uses the artifact’s documented raw check-only interface and identifies its bytes explicitly; it does not claim new build qualification. The official checker’s source bytes match the retained kernel used for this workload.
