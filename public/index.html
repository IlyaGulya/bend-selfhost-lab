Architecture details and official comparison

Official compiler · TypeScript

  1. Parse source into core terms
  2. Check bodies and add annotations
  3. Prepare shared data and find reachable code
  4. Analyze target data and generate C or JavaScript

C sharing analysis computes backend facts. It does not repeat source type checking.

Self-hosted compiler · Bend

  1. Store source terms and checked occurrences
  2. Transfer the owned CheckedProgram
  3. Run shared lowering to backend IR
  4. Analyze target data and generate C or JavaScript

Both compilers use IR. This structure alone does not prove a speed improvement.

Checking resolves names, types, use limits and structural termination. Explicit unsafe forms allow exceptions. Failed checking returns a diagnostic. It does not return a partly checked program.

Lowering converts checked data into operations. It removes erased runtime parameters, resolves captures and calls, and builds pattern control flow. Descriptors retain layout, display and host-interface metadata.

C still plans layouts, sharing and runtime tables. JavaScript still plans continuation captures, frames and host conversion. Source pools use numeric handles and start/count slices. Occurrences and blocks remain recursive. Pool growth can copy storage.

Scratch epochs invalidate temporary substitution-cache entries. This mechanism does not prove lower garbage-collection cost. Execution chunks and the JavaScript trampoline are runtime mechanisms, not additional IR formats.

Input, memory scope and phase times

On 7 November 2026, each compiler checked the same input in three separate processes. The input has 17 Bend modules and 35 foreign JavaScript files. The small example above is a different input.

RSS means resident memory. Sampling includes compiler startup and shutdown across the compiler-command process tree. It excludes the guardian and measurement parent. One MiB is 1,048,576 bytes. These samples are not phase-local allocation counts or universal memory estimates.

The official compiler orders template work differently. Compare combined source-processing times only. Do not compare isolated native phase times with official phase times. The ratio uses the two measured medians.

The native input contains 1,690,863 Bend bytes and 78,415 foreign JavaScript bytes. It includes interfaces with up to 50 arguments and the complete 66,793-byte resume dispatcher. Namespaces, foreign alternatives and dependencies are retained. No bodies were replaced with stubs. CPU-coverage analysis was inconclusive. This input is not a proven representative of every workload.

Native run 3: parse 6.198936 s; expand 1.834936 s; check 19.672753 s; total 27.706625 s. These are one run’s times, not separate phase medians. Parser-fuel setup takes 1.318933 s within parse. It creates 136,000,000 cells across 17 modules. The 1,975,761 checking-chunk advances count resumptions, not source operations or machine instructions. Neither count proves avoidable work.

Host, runtimes and measurement limits

Architecture links refer to the source revision below. Timings use a historical diagnostic -O1 native executable with a recorded hash. This is not a new compiler build or the official default C optimization. The source-authentication wrapper rejects changed lexer and driver inputs. Measurements use the documented raw check-only interface. They do not certify a new build. Official checker bytes match the retained kernel.

Host and date
7 November 2026, 07:42–07:43 UTC. Apple M1 Max, 10 logical CPUs, 64 GiB RAM; arm64 MacBookPro18,4. macOS 26.6.2 (25G83), Darwin 25.6.0.
Run order
Three separate process pairs: official/native, native/official, official/native. No process reuse, profiler, forced garbage collection or removed warmup runs. Filesystem and OS caches were not cleared.
Timed work
Official: load, parse, expand and check. Native: parse, expand and check, including parser-fuel setup. Startup, code output and external C compilation are excluded. The ratio compares source-processing medians.
Official runtime
Node 23.11.0, V8 12.9.202.28-node.14; --experimental-strip-types --max-old-space-size=6144 --max-semi-space-size=128. Worker limits: 6,144 MiB old generation, 128 MiB young generation and 256 MiB stack. Node may use helper threads.
Native runtime
Cached diagnostic -O1 split-LLVM executable. One compute thread; GPU disabled: +RTS --threads 1 --gpu off --RTS. Each run creates 17 parser-fuel rows of 8,000,000 cells. Parse, expansion and checking run in that order.
Memory limits
Bun 1.4.3 starts a guardian. It samples the compiler-command process tree every 10 ms. Official samples include the Node main process and worker. Native samples include its process. The Bun launcher, guardian and measurement parent are excluded. Sampled RSS and physical-footprint limits are each 8,192 MiB. Timeout: 600 seconds. Termination grace: 1 second. These sampled limits are not hard allocation limits or exact peaks.
Completion
All six runs passed the limits. Official checked the 52-file input, 2,420 definition bodies and 2,954 validation events. There were no holes or unchecked bodies. Native returned CheckSuccess for all 17 modules. No checks were excluded or outputs changed. Foreign JavaScript files belong to the input. Their output and execution are not timed.
Input identity
Source files, runtime/compiler files, manifests, records and method scripts were hashed before and after every run and the full comparison. The unmeasured parent used 64 KiB hashing buffers. Sorted source-tuple SHA-256: 2555918b9caf261ab6a85fad8ef8fb132a87d9c835b77ee3a86cdefaed1dca01.
